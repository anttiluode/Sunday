# Sunday gate protocol

Sunday uses gates because the project spans conversations and because rich mechanisms are easy to rationalize after the fact.

A gate is a small executable question with a preregistered receipt.

## Gate template

Each gate document must contain:

### Question
One sentence. Avoid a bundle of claims.

### Candidate mechanism
What new state, coupling, update rule, geometry, or observation is being introduced?

### Held fixed
List the resources and structure that are intentionally matched across arms.

### Arms / controls
At minimum include the simplest null that could explain the result. Add shuffle, clamp, reset, or matched-capacity attackers when they directly address the mechanism.

### Metrics
Prefer measurements that expose *how* the mechanism works, not only task accuracy.

### Receipt
Numerical conditions that must be true before the result is described as surviving the gate.

### Stop lines
Conditions that kill or demote the mechanism.

### What the gate does not establish
Explicitly wall off stronger interpretations.

## Mainline rule

`main` contains only:

- the current research charter;
- accepted receipts and concise summaries;
- kill ledger;
- handoff/current-state documents;
- utilities that later gates depend on.

An experiment begins on a branch named roughly:

```text
sol/gate<N>-short-description
```

A gate branch may be messy. Main should not be.

## Receipt rule

A visually pleasing run is not a receipt.

A receipt should be reproducible from a command and should print or save the decisive metrics. Randomized controls report their seed and distribution. Resource quantities that matter to the claim are printed too.

## Handoff rule

Before a break or major branch transition, update `HANDOFF_CURRENT.md` with:

1. exact branch and gate;
2. what was actually observed;
3. what remains only interpretation;
4. commands to reproduce the current receipt;
5. next falsifier;
6. things the next instance must *not* silently change.

The handoff is a message to the next model instance, not a polished paper abstract.

## Sunday gate map

This map is provisional; later gates earn their existence.

### Gate 0 — signal-carved 3-D microarbor

Can a fixed amount of slow structural mass, redistributed by traversing signal inside a fixed 3-D cloud, create a spatially specific transfer operator?

The strongest immediate attacker is a mass shuffle among unchanged positions: same scalar values, different geometry.

### Gate 1 — history, not just exposure

Only if Gate 0 survives: can the same event multiset in different temporal order produce persistently different transfer geometry? This is where hysteresis/path dependence belongs.

### Gate 2 — local transfer rig

Measure the frozen material as an operator rather than through one soma scalar. Build a terminal/perturbation-to-future-response atlas and ask whether different learned regions expose different local modes.

### Gate 3 — autonomous passing modes

Only after the static/frozen transfer object is understood: add internal phase or autonomous dynamics and test whether useful regimes are generated by the material rather than by an external schedule.

### Later, if earned

Growth/topology changes, world-model binding, learned 3-D decoders, visual manifolds, cross-modal resonance, and branching/self-similarity are parked. None are prerequisites for Gate 0.
